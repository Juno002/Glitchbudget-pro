

# GLITCHBUDGET PRO — ROADMAP 

## Instrucción inicial para Codex:

> **Do not implement this roadmap in one pass. Work strictly phase by phase. Before modifying a phase, inspect the current implementation and its tests. Preserve all existing user data through explicit Dexie migrations. Never reset the database as a migration strategy. Do not use the README as the functional specification. Do not introduce a backend, cloud synchronization, remote AI, analytics, advertising, remote financial APIs, or any mechanism that sends user financial data off-device. Prefer extending or migrating the working system over rewriting it. At the end of every phase, run all checks, verify backup compatibility and offline behavior, report architectural concerns, and STOP for review before beginning the next phase.**


## Objetivo del producto

GlitchBudget Pro es una aplicación financiera **personal, local-first y offline-capable**.

La aplicación debe permitir administrar cuentas, movimientos, tarjetas, presupuestos, planificación, metas, inversiones y análisis **sin transmitir información financiera fuera del dispositivo**.

No implementar:

- cuentas de usuario de GlitchBudget;
- backend de aplicación;
- sincronización bancaria;
- sincronización cloud;
- IA remota;
- telemetría financiera;
- publicidad;
- servicios de terceros que reciban movimientos, saldos, categorías, metas o inversiones;
- cotizaciones o tipos de cambio obtenidos automáticamente desde Internet;
- Web Push dependiente de servidor;
- colaboración o cuentas compartidas.

La PWA puede descargar/actualizar sus **archivos estáticos** desde su origen de distribución. Eso no autoriza a transmitir datos financieros.

**El código actual de `main` es la fuente de verdad. El README está desactualizado y no debe utilizarse como especificación.**

# Arquitectura objetivo

Antes de seguir añadiendo funciones, el código debe evolucionar hacia cuatro capas:

```text
UI
 ↓
Application services / commands
 ↓
Domain calculations / selectors
 ↓
Dexie / local persistence
```

Reglas:

```text
UI ≠ reglas financieras
UI ≠ acceso directo a Dexie

Dexie ≠ cálculos financieros

Domain ≠ React
Domain ≠ navegador
Domain ≠ red
```

Los cálculos de saldo, presupuesto, deuda, cash flow, metas e inversiones deben poder probarse como funciones puras.

No hacer un rewrite completo. Migrar gradualmente el código existente hacia esta estructura.

---

# Invariantes financieros

Estas reglas deben quedar documentadas y probadas **antes de añadir nuevas funciones**.

```text
Ingreso
→ aumenta una cuenta
→ cuenta como ingreso

Gasto con efectivo/banco
→ reduce una cuenta
→ cuenta como gasto

Compra con tarjeta
→ aumenta gasto
→ aumenta pasivo
→ NO reduce efectivo todavía

Pago de tarjeta
→ reduce una cuenta
→ reduce pasivo
→ NO vuelve a contar como gasto

Transferencia
→ reduce una cuenta
→ aumenta otra
→ NO cambia patrimonio
→ NO es ingreso
→ NO es gasto

Presupuesto
→ planificación
→ NO mueve dinero

Pago planificado
→ planificación
→ NO mueve dinero hasta confirmarse

Meta
→ seguimiento/reserva
→ NO altera patrimonio por sí sola

Inversión financiada desde una cuenta
→ mueve patrimonio líquido a patrimonio invertido
→ NO es gasto

Rendimiento proyectado
→ estimación
→ NO se convierte automáticamente en patrimonio real
```

Además, todos los importes monetarios almacenados deben seguir usando **enteros en unidades mínimas** —centavos actualmente— y nunca `float` para dinero almacenado.

# FASE 2 — Crear el núcleo financiero canónico

Esta es probablemente **la fase más importante de todo el roadmap**.

Actualmente hay cálculos repartidos entre:

```text
finance-context.tsx
finance-calculations.ts
accounts.ts
transaction-service.ts
budget-rollover.ts
varios componentes
```

Crear un dominio financiero central.

Por ejemplo:

```text
src/domain/
  money.ts
  dates.ts
  ledger.ts
  accounts.ts
  liabilities.ts
  periods.ts
  budgets.ts
  goals.ts
  recurrence.ts
  investments.ts
  reports.ts
```

No es obligatorio usar exactamente esos nombres, pero sí separar responsabilidades.

## 2.1 Definir métricas distintas

No utilizar palabras ambiguas como simplemente `balance`.

Definir al menos:

### Liquid position

```text
cash + bank accounts
```

### Net worth

```text
assets - liabilities
```

### Spending

Compras/gastos realizados, incluyendo compras a crédito.

### Cash flow

```text
cash income
- cash expenses
- debt payments
```

Las transferencias quedan fuera.

### Available to plan

Concepto de planificación:

```text
income/capacity
- commitments
- reserved budget
- goal allocations
```

No confundirlo con saldo bancario.

Esto evitará que Home, Reports y Accounts terminen mostrando números diferentes con el mismo nombre.

# FASE 3 — Corregir el ledger actual antes de ampliarlo

## 3.1 Nuevos ingresos

Actualmente `saveIncome()` asigna automáticamente una nueva entrada a Efectivo.

Cambiar esto.

Si el usuario selecciona:

```text
Qik
APAP
Efectivo
```

el ingreso debe afectar esa cuenta.

Efectivo solo debe ser el default, no una obligación.

## 3.2 Eliminaciones

Actualmente la eliminación de ingresos pasa por el servicio financiero, pero `deleteExpense` puede borrar directamente desde `finance-context.tsx`.

Toda modificación financiera debe pasar por comandos transaccionales comunes:

```text
create
update
delete
```

para que las mismas invariantes se cumplan siempre.

## 3.3 Strict Mode

Actualmente mezcla dos problemas:

```text
¿puedo dejar una cuenta negativa?
```

y:

```text
¿estoy superando lo que había planificado?
```

Separarlos.

Por ejemplo:

```text
preventNegativeAccountBalance
budgetOverspendingBehavior
```

El segundo podría ser:

```text
allow
warn
block
```

No utilizar una sola bandera para ambos conceptos.

## 3.4 Integridad histórica

Las entidades utilizadas por transacciones no deberían desaparecer destructivamente.

Preferir:

```text
Account → archive
Category → archive
Credit card → close
Investment → close
Recurring rule → deactivate
```

en lugar de borrar referencias históricas.

# FASE 4 — Normalizar categorías antes de Rules/Reports/Templates

Actualmente las categorías predeterminadas están en `categories.ts`, mientras la configuración mantiene arrays de strings y custom icons.

Eso funcionó bien para empezar, pero se volverá frágil con:

- renombrado;
- categorías archivadas;
- templates;
- filtros;
- reglas;
- análisis históricos.

Migrar a categorías con identidad estable:

```ts
Category {
  id
  name
  type: income | expense | both
  icon
  archived
}
```

Un rename cambia `name`, **no `id`**.

Migrar todas las referencias actuales preservando los IDs existentes.

Los defaults pueden seguir creándose automáticamente.

### Gate 4

Renombrar una categoría no debe modificar ni perder la categorización histórica.

# FASE 5 — Resolver definitivamente Actual vs Planned

Actualmente hay una superposición importante.

`Expense` puede ser `Fijo` y tener `frequency`, mientras existe además `Recurring`.

Eso debe desaparecer antes de mejorar Planned Payments.

Una transacción real representa **algo que ocurrió**.

Nunca debe representar implícitamente:

> “y repite este gasto todos los meses para siempre”.

Por tanto:

```text
Expense
= hecho real

RecurringRule
= intención futura
```

`Fijo / Variable / Ocasional` puede conservarse como **clasificación del gasto**, pero `frequency` no debe hacer aparecer gastos futuros dentro del ledger real.

Eliminar gradualmente `expenseForMonth()` como mecanismo que replica gastos fijos hacia meses posteriores.

# FASE 6 — Construir un motor de períodos antes de Budgets 2.0

Actualmente muchos sitios utilizan:

```ts
date.slice(0, 7)
```

y `month: YYYY-MM`.

Eso funciona únicamente mientras todo significa “mes calendario”.

Antes de permitir:

```text
Weekly
Monthly
Yearly
One-Time
Financial month starting on day 25
```

crear un motor común:

```ts
DateRange {
  start
  end
}
```

con funciones como:

```text
periodContaining(date, settings)
previousComparablePeriod(period)
nextPeriod(period)
contains(period, date)
```

Los reportes y presupuestos nuevos deben trabajar con rangos de fecha, no con substring de `YYYY-MM`.

### Importante

`Income.month` y `Expense.month` son derivables desde `date`.

No tienen que eliminarse inmediatamente del DB si complicaría la migración, pero **deben dejar de ser fuente de verdad**.

Lo mismo aplica a `Period` si deja de aportar información útil.

### Gate 6

Cambiar el inicio del período de:

```text
1
```

a:

```text
25
```

debe producir correctamente:

```text
25 agosto → 24 septiembre
```

en todos los cálculos que utilicen el nuevo motor.

# FASE 7 — Motor real de Planned Payments

Reemplazar la actual lógica de “una suscripción ya registrada en este mes” por ocurrencias reales.

Actualmente esa regla mensual también impediría manejar correctamente recurrencias semanales/quincenales.

Modelo conceptual:

```ts
RecurringRule {
  id
  direction
  title
  amount
  categoryId
  defaultAccountId?
  cadence
  startDate
  endDate?
  active
  ...
}
```

y:

```ts
PlannedOccurrence {
  id
  ruleId
  scheduledDate
  status: pending | confirmed | skipped
  transactionId?
}
```

La combinación:

```text
ruleId + scheduledDate
```

debe ser única.

Así:

```text
Netflix · Sep 28 · Pending
```

puede pasar a:

```text
Netflix · Sep 28 · Confirmed → Expense abc123
```

Confirmarlo dos veces debe ser imposible.

### Weekly / Biweekly

Debe basarse en intervalos reales desde la fecha de inicio, no:

```text
4.33 por mes
```

### Día 29–31

Definir una sola política.

Recomendación:

> si el mes no contiene ese día, utilizar su último día válido.

Documentarlo y probarlo.

### Upcoming

Generar localmente:

```text
Today
Tomorrow
Next 7 days
Later
```

No necesita servidor.

# FASE 7.5 — UX Architecture & Design System

Esta fase ocurre **después del motor de recurrencias/Planned Payments y antes de Quick Add 2.0**.

El objetivo no es rediseñar visualmente toda la aplicación todavía. Es definir una arquitectura de interacción y un sistema visual estable para que las siguientes fases no creen pantallas incompatibles entre sí.

No implementar features nuevas en esta fase salvo los cambios mínimos necesarios para establecer los patrones.

---

## 7.5.1 — Definir la arquitectura de información

Mantener cuatro áreas principales:

```text
Resumen
Movimientos
Plan
Reportes
```

No añadir nuevas pestañas principales para:

```text
Cuentas
Tarjetas
Metas
Inversiones
Suscripciones
Ajustes
```

Esas funciones deben vivir dentro de las cuatro áreas principales o en navegación secundaria.

### Responsabilidad de cada área

**Resumen**

Debe responder:

```text
¿Cuánto tengo?
¿Cuánto debo?
¿Cuánto puedo gastar?
¿Qué viene próximamente?
¿Qué requiere atención?
```

No debe convertirse en una colección de reportes.

**Movimientos**

Debe ser la fuente principal para consultar actividad financiera real:

```text

Gastos
Transferencias
Pagos de deuda
```

y posteriormente:

```text
búsqueda
filtros
edición
agrupación por fecha
```

**Plan**

Contendrá:

```text
Presupuestos
Metas
Planificados
```

No mezclar movimientos realizados con planificación.

**Reportes**

Contendrá análisis histórico y comparaciones:

```text
Spending
Cash flow
Net worth
Comparisons
Trends
```

# FASE 19.5 — Residual architecture cleanup / Prisma Engine Gate

Esta fase ocurre **después de cerrar la Fase 19** y antes de considerar estable el núcleo reutilizable.

La Fase 19 elimina la deuda técnica estructural conocida. La Fase 19.5 debe asumir que pueden quedar residuos pequeños o indirectos y realizar una auditoría exhaustiva de frontera entre UI, aplicación, dominio y persistencia.

Objetivo:

```text
dejar el núcleo financiero de GlitchBudget reutilizable por una interfaz distinta
sin depender de componentes React, decisiones visuales ni acceso a persistencia desde UI
```

No añadir features nuevas durante esta fase.

## 19.5.1 — Auditoría completa de la capa visual

Revisar, como mínimo:

```text
src/components/**
src/hooks/**
src/contexts/**
src/app/**
```

Buscar cualquier resto de:

- cálculos financieros;
- invariantes o reglas de negocio;
- clasificación financiera;
- construcción de read models financieros;
- decisiones de dominio basadas en saldo, deuda, presupuesto, metas, inversiones o recurrencias;
- acceso directo a Dexie;
- mutaciones directas de datos financieros;
- transformaciones que determinen el significado financiero de una entidad.

La auditoría no debe limitarse a archivos ya conocidos en Fase 19.

## 19.5.2 — Cero acceso financiero directo a Dexie desde UI

Después de esta fase, los componentes visuales no deben ejecutar:

```ts
db.*
useLiveQuery(() => db.*)
```

para leer o modificar datos financieros.

Mover esos accesos a queries, repositories, application services o fachadas apropiadas.

Los hooks y contexts de React tampoco deben convertirse en una vía alternativa para esconder acceso directo a persistencia financiera.

Excepciones de persistencia puramente visual/local —por ejemplo preferencias de apariencia— deben quedar explícitamente documentadas y no contener datos ni reglas financieras.

## 19.5.3 — Cero cálculos financieros canónicos en componentes

Extraer de UI cualquier cálculo que determine o derive conceptos como:

```text
liquid position
net worth
spending
cash flow
available to plan
budget spent / remaining / status
debt / available credit
goal progress / required contribution
investment current value / projection
period deficit / surplus
planned-payment status
```

La UI puede convertir un valor ya calculado en una representación visual —por ejemplo ancho de una barra, coordenadas SVG o formato de moneda—, pero no debe decidir el significado financiero de ese valor.

Ejemplo:

```text
Permitido en UI:
percentForProgressBar = clamp(domainPercentage)

No permitido en UI:
remaining = budgetLimit - spending
```

## 19.5.4 — Read models reutilizables

Las pantallas complejas deben consumir read models/selectores ya resueltos.

En particular, revisar que superficies como:

```text
Resumen
Movimientos
Plan
Reportes
Cuentas
Metas
Inversiones
Planificados
```

no reconstruyan por su cuenta relaciones entre ingresos, gastos, transferencias, pagos de deuda, aportes, cuentas o saldos iniciales.

Cuando una pantalla necesite una vista compuesta, crear una query/selector/read model reutilizable independiente de React.

## 19.5.5 — `finance-context` como fachada, no motor

Verificar nuevamente `finance-context.tsx` después de la Fase 19.

Debe limitarse principalmente a:

- composición de estado React;
- exposición de commands/queries;
- coordinación de interacción;
- adaptación mínima para la UI.

No debe contener:

- fórmulas financieras;
- reglas de negocio;
- consultas Dexie que pertenezcan a repositories/queries;
- validaciones financieras canónicas;
- construcción de reportes;
- lógica propia de presupuestos, metas, deuda o inversiones.

Si alguna de esas responsabilidades permanece, extraerla antes de cerrar 19.5.

## 19.5.6 — Reglas automáticas para impedir regresiones

Añadir o endurecer checks estáticos.

Como mínimo:

- `no-restricted-imports` para impedir importar `@/lib/db` o Dexie desde componentes;
- regla equivalente para impedir `db.*` en UI;
- pruebas o checks que fallen si selectores/servicios de dominio empiezan a depender de React;
- búsqueda automatizada de accesos de persistencia financiera dentro de `src/components`, `src/hooks`, `src/contexts` y `src/app`.

El objetivo es que la separación no dependa de disciplina manual futura.

## 19.5.7 — Auditoría de residuos pequeños

Revisar explícitamente lógica que puede parecer inocente por ocupar una sola línea, incluyendo:

- `reduce()` de importes;
- `limit - spent`;
- `income - expenses`;
- porcentajes con semántica financiera;
- detección de estados como `over`, `completed`, `overdue`, `deficit` o `surplus`;
- selección automática de cuenta/categoría basada en reglas financieras;
- combinación de entidades de varias tablas para crear un movimiento o métrica;
- validaciones monetarias que deberían pertenecer a commands/domain.

No conservar una regla en UI únicamente porque sea pequeña.

## Gate 19.5 — Prisma Engine Gate

La fase solo se considera cerrada cuando se puede afirmar y demostrar:


# Definition of Done obligatoria para CADA fase

Codex **no debe pasar automáticamente a la fase siguiente**.

Cada fase termina únicamente cuando:

```text
npm run typecheck
npm run lint
npm test
npm run build
```

están verdes.

Además:

```text
existing backup import works
export/import round-trip works
existing financial totals remain valid
new migrations have tests
offline mode still works
no financial network traffic introduced
```

Y Codex debe entregar antes de continuar:

```text
1. Files changed
2. Schema changes
3. Migration behavior
4. Invariants affected
5. Tests added
6. Known limitations
7. Any architectural concern discovered
```

Si encuentra que una fase posterior requiere cambiar una decisión estructural anterior, **debe detenerse y señalarlo antes de implementar**, no construir un workaround.
