# 20.7.5.7 — Ledger performance baseline

Authority: `Roadmap septiembre 2026.txt`, Phase 20.7.5.7.

## Decision

**Baseline measured. No optimization is justified in this microintervention.**

The current canonical selectors remain unchanged. No persistent cache, secondary financial source, materialized ledger index, schema migration, backup change, UI change, or network dependency is introduced.

## Benchmark harness

`scripts/benchmark-ledger.mjs` generates deterministic mixed financial datasets with:

- 8 accounts;
- income;
- cash expenses;
- debt payments;
- transfers;
- 1,000 / 10,000 / 50,000 total movements;
- one canonical position read;
- per-account history reads for all 8 accounts.

The benchmark performs one warm-up and seven measured samples per operation. Timings are informational: CI records them, but no unstable millisecond threshold is turned into a test.

## CI baseline

Reference environment: GitHub Actions / Node 22, Quality checks `36795170833`.

| Movements | `selectPosition()` median | 8-account histories median |
| ---: | ---: | ---: |
| 1,000 | 0.59 ms | 0.51 ms |
| 10,000 | 5.66 ms | 6.10 ms |
| 50,000 | 32.22 ms | 23.68 ms |

Raw samples remain available in the workflow log.

## Interpretation

The benchmark confirms growth with dataset size, as expected from selectors that filter in-memory collections. At the roadmap's 50,000-movement stress case, both measured operations remain in the tens-of-milliseconds range on CI hardware.

That is measurable scaling, but not evidence of a user-facing performance problem that justifies additional architectural complexity. In particular:

- `selectAccountEntries()` does not require a new persistent cache;
- `selectPosition()` does not require a materialized second source of truth;
- no grouping/index optimization is introduced speculatively;
- future optimization must compare against this same reproducible baseline.

Memory is not promoted to a gate metric here because process heap readings on shared CI are too noisy to serve as a stable baseline, and the implementation introduces no persistent duplication.

## Reproduction

```bash
npm run benchmark:ledger
```

The normal Quality checks workflow also executes the benchmark as an informational step before build/E2E.

## Gate

20.7.5.7 is closed because:

1. the required 1k/10k/50k baseline exists;
2. position and per-account history are measured;
3. the benchmark is reproducible in CI;
4. no optimization is applied without evidence;
5. no second financial source of truth is created.
