# 20.7.5.6 — Encrypted Backup v2 assessment

Authority: `Roadmap septiembre 2026.txt`, Phase 20.7.5.6.

## Baseline audited

The current encrypted backup is envelope v1 and uses only browser Web Crypto:

- PBKDF2-HMAC-SHA-256;
- 310,000 iterations;
- 16-byte random salt;
- AES-256-GCM;
- 12-byte random nonce;
- 128-bit authentication tag;
- authenticated AAD covering format, version, KDF and cipher metadata;
- password accepted at 8–128 characters;
- no password persistence or transmission;
- normal JSON backup remains separate and available.

Existing v1 restore behavior deliberately collapses wrong-password and authenticated-decryption failure into the same user-facing error.

## Current guidance reviewed

Assessment date: 2026-09-30.

OWASP Password Storage Cheat Sheet currently recommends PBKDF2-HMAC-SHA-256 at 600,000 iterations for password hashing when PBKDF2 is used. That number is treated here as a conservative reference point, not as a direct requirement for password-based backup encryption. NIST SP 800-132 remains the directly relevant password-based key-derivation publication for storage applications; NIST has announced a revision intended to add memory-hard guidance and clarify PBKDF2.

References:

- https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html
- https://csrc.nist.gov/pubs/sp/800/132/final
- https://www.nist.gov/news-events/news/2023/05/nist-revise-sp-800-132-recommendation-password-based-key-derivation-part-1

## Reproducible benchmark

`scripts/benchmark-encrypted-backup.mjs` measures PBKDF2 key derivation without changing production parameters.

Reference run on the available desktop Node/Web Crypto runtime, five samples after key import:

| PBKDF2-SHA-256 iterations | samples (ms) | median |
| --- | --- | ---: |
| 310,000 | 65.7, 68.0, 71.8, 75.9, 88.4 | 71.8 ms |
| 600,000 | 128.9, 130.8, 131.5, 133.2, 137.3 | 131.5 ms |

This demonstrates that 600,000 iterations are practical on the measured desktop runtime, but it is not a representative physical-mobile benchmark. Browser viewport/device emulation would still execute on desktop hardware and therefore is not accepted as evidence of mobile KDF latency.

Project latency budget for a future format change (an engineering target, not an external cryptographic standard):

- target: <= 750 ms per password-based key derivation on a representative mid-range mobile device;
- hard review threshold: 1,000 ms;
- export/import may each pay one derivation, but routine financial operations must pay none.

## v2 decision

**Do not introduce envelope v2 in 20.7.5.6. Keep export on v1 and keep v1 import compatibility unchanged.**

Reasoning:

1. 310,000 PBKDF2-SHA-256 iterations are below OWASP's current 600,000 recommendation, so a future increase has a concrete security rationale.
2. The roadmap explicitly forbids choosing a higher iteration count without benchmark evidence.
3. The available desktop measurement supports 600,000, but there is no representative physical-mobile measurement in this repository/CI environment. Selecting 600,000 as a production default now would therefore violate the benchmark requirement rather than satisfy it.
4. Web Crypto does not provide Argon2id/scrypt as native interoperable algorithms here; adding a new local dependency/WASM KDF would enlarge the security and compatibility surface and is not justified without a measured requirement.
5. v1 already provides authenticated encryption, random salt/nonce, authenticated metadata, and backward-compatible local-only restore. There is no demonstrated cryptographic-format defect requiring an emergency format bump.

A future v2 is authorized only by a new roadmap decision after representative mobile measurement demonstrates the chosen KDF/work factor fits the latency budget. If v2 is later introduced, v1 import must remain readable and v1 files must never be rewritten automatically.

## Password policy assessment

No password-length change is made here. Increasing the minimum from 8 without a versioned UX/format transition would change current export behavior while providing no substitute for KDF benchmarking. The current 128-character maximum remains a resource bound, not an entropy claim.

## Compatibility / invariants

20.7.5.6 intentionally changes no production crypto, schema, Dexie migration, JSON backup version, network behavior, UI financial logic, or persistence boundary.

Required invariants remain:

- encrypted envelope version = 1;
- Backup JSON version = 13;
- Dexie schema version = 15;
- v1 import/export remains supported;
- wrong password and tampered ciphertext remain indistinguishable at the user-facing decrypt boundary;
- password is neither stored nor transmitted;
- `connect-src 'none'` / local-only architecture remains intact.

## Gate decision

20.7.5.6 is an assessment gate, not a mandatory format bump. Its outcome is **v2 not justified yet** because the stronger candidate work factor lacks representative mobile benchmark evidence. The current format remains frozen and compatibility is protected by regression tests.
